# 产品简报 · 让 AI 教练的输出质量可以被回归

> 产出工作流：`/bmad-product-brief`（Analyst）
> 项目：骑行评分监测看板（cycling-dashboard）｜Epic 2
> 日期：2026-11-04
> 状态：已定稿，交 `/bmad-prd` 继续

---

## 一、一句话

评测工具已经写好了，**但没有任何机制让它被跑起来**。这次要补的不是"再写一个评测"，而是"让评测变成流程的一部分"——改完提示词，机器告诉你有没有退步。

## 二、问题是什么（先给实测，不给推测）

### 证据 1：我刚刚真跑了一次，6 条用例挂了 1 条

```
$ cd server && npm run eval
· hot-long … ok
· climb-heavy … ok
· rainy … ok
· sparse-data … ok
· bad-air … ok
· improving-trend … FAIL        ← 退出码 1

用例：6 个，全部检查通过：5 个
token 合计：4738 ｜ 平均耗时：2227 ms
```

挂的这条，失败原因是**「未编造信息」**：

```
意图：历史三次距离与均速持续上升：应识别出趋势并给出下一档目标，而不是只描述当天
- 未通过  未编造信息 —— 凭空断言：心率、功率
```

**心率、功率这两个维度，输入数据里一个都没有。** 这是本项目 AI 链路里最严重的失败模式——
不是"写得不好"，是"说了不存在的事实"。而它一直没被发现，因为**没人跑评测**。

### 证据 2：工具自己都写好了"该挂进 CI"，但没挂

`server/eval/run.ts` 第 15–17 行的注释原文：

> 有任一用例不达标 → 退出码 1，**因此可以直接挂进 CI**：改 prompt 的提交如果让质量退步，流水线会拦下来

而 `.github/workflows/ci.yml` 的四道闸门是 lint / 前端测试 / 后端测试 + 类型 / 构建——**没有评测**。
工具留了接口，流程没接上。

### 证据 3：项目自己把这条写进了"已知问题"

补充说明的「5. 当前完成情况与已知问题」里，第 ② 条原文：

> AI 教练的回复质量目前靠人工看，尚未建立离线评测集，**无法量化"改了一次提示词到底变好还是变差"**

### 证据 4：地基是好的，缺的是"谁跑、跟谁比"

`server/test/eval.test.ts` 有 13 条单测，专门守"判定规则本身对不对"（用一条明确的好输出和一条明确的坏输出做对照）。
也就是说 **"怎么判"这件事已经可信了**，缺的是环节串联：跑 → 记录 → 下次对比 → 退步就红。

## 三、为什么现在做、为什么值得做

| 理由 | 说明 |
|---|---|
| 这是项目自认的短板 | 证据 3，不是外部要求硬塞的 |
| 改 prompt 是高频动作 | 提示词一改，输出风格、长度、是否编造都会变；靠肉眼看几条根本发现不了退化 |
| 成本已经很低 | 6 条用例每次约 4.7k token，跑一次几秒钟 |
| 顺手补上一个真实缺陷 | 证据 1 那条编造，本身就该修 |

## 四、给谁用

| 角色 | 诉求 |
|---|---|
| **站长本人**（改提示词的人） | 改完立刻知道"这次是变好还是变差"，而不是上线后靠感觉 |
| 仓库访问者 | 看到"这个项目对 AI 输出有质量门"，而不是"接了个大模型就算 AI 功能" |
| 未来的自己 | 三个月后想调 prompt，有基线可比，不至于把已经踩过的坑再踩一遍 |

## 五、目标

1. **一条命令出结论**：跑完直接告诉你"通过 N/6、与基线相比退化了哪几项"。
2. **退化必须红**：任何用例从通过变不通过，退出码非零。
3. **不烧钱地进 CI**：CI 里跑的那一步**不能**真实调用模型（每次 push 都花钱、且模型输出随机会让流水线变成偶发红灯）。
4. **真实调用仍然保留**：有 key 时手动跑，测的是"当前 prompt 的真实水平"。

## 六、非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 在线 A/B / 灰度分流 | 单人项目、日活个位数，A/B 没有统计意义 |
| 接多个模型横向对比 | 成本翻倍、结论噪音大；先把一个模型守住 |
| 人工标注平台 / 评分后台 | 6 条用例用不着平台，YAML/JSON 手改更快 |
| 自动修改提示词（自优化） | 危险且不可解释；本项目要的是"能发现退化"，不是"自动变好" |

## 七、怎么算成功

| # | 判据 | 验证方式 |
|---|---|---|
| 1 | 有 key 时能跑真实评测，并输出与基线的逐项对比 | 本地真跑一次，看报告 |
| 2 | 无 key 时能跑离线检查（确定性，不调模型） | 清空 key 环境变量后跑，仍能给出结论 |
| 3 | 退化能让退出码非零 | 人为把某条用例的基线改成"全过"再跑离线，应当报退化 |
| 4 | CI 里有这一步，且不需要 secret | workflow 里加 step，`permissions` 仍为只读 |
| 5 | 实测那条编造问题有明确处置 | 记录在审查/验证报告里，说明是修 prompt 还是先记为已知问题 |

## 八、交给下一阶段的问题

1. 基线文件要不要进仓库？（进：可回归、可审计；不进：仓库干净但历史丢失）
2. 离线模式守的是什么？（判定规则不回归 vs 模型不退化——两者能力不同，必须说清楚，不能让人误以为"离线绿=质量好"）
3. 那条编造问题本轮修不修？（修 prompt 会牵动其它用例，可能超出本期范围）
