# 产品简报 · 提交即验证的 CI 流水线

> 产出工作流：`/bmad-product-brief`（Analyst）
> 项目：骑行评分监测看板（cycling-dashboard）
> 日期：2026-11-04
> 状态：已定稿，交 `/bmad-prd` 继续

---

## 一、一句话

给这个已经有 182 个测试、却**只有人想起来才跑**的项目，装一条"推上去就自动验"的流水线：lint、测试、构建三道门，任何一道不过就红，红了的代码不允许合进 `main`。

## 二、问题是什么（先把证据摆出来）

这不是"别人项目都有 CI 所以我也要"。这个项目的问题在自查文档里就已经写明，只是没人去补：

| 证据 | 出处 | 说明 |
|---|---|---|
| 自述短板 | `docs/技术架构与设计取舍.md:255` | 原文："为什么没有 CI/CD？现在是手动构建上传。**这是明确的短板** —— 下一步就做 GitHub Actions：push 后自动跑测试 + lint + 构建，通过才发布。" |
| 仓库确实没有 | `.github/` 不存在（已核查） | 从 2026-09-14 首次提交到 2026-11-04，62 次提交，零次自动化验证 |
| 测试是真的，但靠自觉 | `npm test` → 14 个文件 / 182 个用例 / 19.5 秒 | 覆盖评分算法、GPX 解析、备份校验、API 客户端等核心逻辑，跑一次不到 20 秒，**却没有任何机制保证它被跑过** |
| 类型检查只在 build 时发生 | `package.json: build = tsc -b && vite build` | 日常开发走 `vite dev`，**不做类型检查**。一个类型错误可以一路提交、直到某次手动 build 才炸 |
| 部署是纯手工 | 手动构建 → 上传服务器 | 漏跑测试、传了旧 `dist`、忘了升版本号，三者都没有拦截 |

**关键判断**：这个项目的工程质量短板不在"写得不够好"，而在"**验证动作依赖人的记性**"。人一忙（比如同时准备实习和专升本），第一件被砍掉的就是跑测试。

## 三、给谁用

| 角色 | 诉求 | 现状痛点 |
|---|---|---|
| **站长本人**（主要用户，单人开发） | 改完推上去就知道有没有搞坏 | 现在只能靠"我记得刚才跑过" |
| **仓库访问者**（教师、面试官、未来协作者） | 5 分钟内判断这仓库能不能跑、代码过不过测试 | 只能自己 `npm i && npm test`，试错成本高 |
| **未来的自己**（接手三个月后的代码） | 改动是否破坏旧行为，有客观答案 | 无 |

## 四、目标

1. **有人推代码，就自动验**：`push` 到任意分支、以及向 `main` 发起 PR 时触发。
2. **三道门，顺序执行，前一道不过就停**：`lint` → `test` → `build`。
3. **失败要说清哪一步、哪一行**：不允许只给一句 "process completed with exit code 1"。
4. **快**：热缓存下全流程 ≤ 5 分钟（本地实测 19.5s 测试 + 9.8s 构建，主要成本在装依赖）。
5. **结果可留存**：构建产物作为 artifact 上传，需要手动部署时可直接下载，不必本地重跑。
6. **状态可见**：README 顶部有流水线状态徽章。

## 五、非目标（明确不做，防止范围失控）

| 不做 | 原因 |
|---|---|
| **自动部署到服务器** | 部署路径、域名、服务器信息按项目既有约定**不进公开仓库**（见 `.gitignore` 中 `server/scripts/`、`server/README.md` 的注释）。把部署塞进公开仓库的 workflow，等于把凭据搬到 GitHub Secrets 里，风险与收益不匹配 —— 这是**取舍，不是遗漏** |
| 多 Node 版本矩阵 | 单人项目，锁一个 LTS 就够；矩阵只会让等待时间翻倍 |
| Docker 化 | 单机面板部署已够用（同 `docs/技术架构与设计取舍.md` 的判断） |
| 覆盖率门禁 | 182 个用例已覆盖核心算法，但仓库没有覆盖率基线。**先有红绿，再谈百分比** —— 一上来设阈值只会逼人写凑数测试 |
| 定时任务 / 夜间构建 | 没有需要定时的东西 |

## 六、怎么算成功

| # | 判据 | 验证方式 |
|---|---|---|
| 1 | 正常代码推上去，三道门全绿 | 真实 push 后的流水线结果 |
| 2 | **故意弄坏，能拦住** | 在分支上注入一处 lint 错误 → 流水线红；还原 → 绿。两次结果都记录在案 |
| 3 | 类型错误能被拦住（不只是 lint） | 注入一处类型错误，确认 `tsc -b` 在 build 阶段拦下 |
| 4 | 热缓存复跑 ≤ 5 分钟 | 记录首跑与复跑耗时 |
| 5 | 本地能跑同一套命令 | `npm run ci` 与流水线执行**完全相同**的脚本，避免"CI 能过、本地跑不了"的双轨问题 |

## 七、风险与假设

| 风险 | 应对 |
|---|---|
| 首次装依赖慢（依赖含高德 SDK、Tailwind、React 全家桶） | 缓存 `~/.npm`；首跑超标就先接受，记录真实数字而不是美化 |
| 云端运行需要仓库在 GitHub 侧且 Actions 可用 | 本机到 `github.com:443` 的 TLS 不通（既有问题），本次以**本地等价命令的真实红绿结果**作为验证证据，云端首跑由站长在能联网的环境补一次截图 |
| 流水线与 Gitee 镜像的关系 | 作业要求提交到 Gitee，项目主仓在 GitHub。**Gitee 作为提交/审阅镜像，流水线定义随仓库走**；若后续迁到 Gitee Go，只需把三个 npm 命令搬进 `.workflow/`，脚本层零改动 —— 这正是"闸门写成 npm script 而不是塞进 yml"的理由 |

## 八、交给下一阶段的问题

1. 三道门要不要允许 `build` 与 `test` 并行？（省时间 vs "先测后用产物"的语义顺序）
2. lint 失败要不要区分"错误"和"警告"？（当前 `eslint .` 零警告，可以严）
3. 分支保护（禁止红灯合并）在**私有单人**场景下是否有必要？还是靠自律 + 徽章可见即可？
4. 失败时的日志要不要落成 artifact，方便事后复盘？
