# PRD · AI 教练输出质量的可回归闸门

> 产出工作流：`/bmad-prd`（PM）
> 上游：`brief-ai-eval-regression.md`
> 版本：v1.0（2026-11-04）｜状态：已确认，交 `/bmad-architecture`

---

## 一、目标复述

评测工具已存在且判定规则可信（13 条单测守着），缺的是**环节**：谁跑、跟谁比、退步了怎么办。
本期把这三个问题补上，并让 CI 能在**不花钱、不依赖模型随机性**的前提下守住它。

## 二、用户故事

| ID | 作为 | 我希望 | 以便 |
|---|---|---|---|
| US-1 | 改了提示词的站长 | 一条命令就知道这次比上次好还是差 | 不用凭感觉 |
| US-2 | 提交代码的我 | CI 能挡住"把判定规则悄悄放宽"的改动 | 质量门不会被自己拆掉 |
| US-3 | 三个月后的我 | 看得到当时的基线长什么样、为什么那条算已知失败 | 不用重新踩坑 |

## 三、功能需求

### FR-1 基线文件（P0）

- 位置：`server/eval/baseline.json`，**进仓库**。
- 内容：模型名、录制时间、每条用例的 `passed`、逐项 `checks` 结果、以及当时的 `review` 原文。
- 理由：它同时承担两个角色 —— **回归基线**（跟上次比）与**离线夹具**（无 key 时重放检查）。

### FR-2 在线评测（有 key，P0）

`cd server && npm run eval`：

1. 真实调用模型跑完 6 条用例（行为不变）；
2. 逐条与基线对比，输出**三分类**：`退步 / 进步 / 不变`；
3. 退出码规则（关键）：
   - 任一条**基线通过、本次失败** → 退出码 1（真回归，必须拦）；
   - 任一条**本次失败且不在 `knownFailures` 里** → 退出码 1（新问题，必须拦）；
   - 失败项**在 `knownFailures` 里** → 只报告，不阻塞（已知问题，例如本轮那条编造）。

### FR-3 已知失败清单（P0）

- 字段：`baseline.json` 的 `knownFailures: string[]`（用例 id 列表）。
- 语义：**"这条现在就是红的，我们知道，正在单独处理"**，不是"把红灯涂绿"。
- 约束：清单只允许**缩小**，不允许新增 —— 新增必须走一次评审并写明原因。

### FR-4 离线评测（无 key，P0）

`cd server && npm run eval:offline`：

1. 不调用模型，把基线里存的 `review` 重新喂给当前的 `runChecks`；
2. 若重放结果与基线记录的 `passed` 不一致 → 退出码 1。

**它守的是"判定规则没被悄悄改松"，而不是"模型没退步"。** 这句话必须同时出现在命令输出和文档里，
避免有人把"离线绿"读成"质量好"。

### FR-5 进 CI（P0）

- 根 `package.json` 增加 `ci:eval`（调用 `npm --prefix server run eval:offline`）；
- `ci` 链变成：`lint → test → server → eval → build`；
- workflow 增加独立 step「AI 评测（离线）」，排在「后端类型与测试」之后、「类型与构建」之前。

### FR-6 更新基线（P1）

- `EVAL_UPDATE_BASELINE=1 npm run eval` 覆盖写 `baseline.json`；
- 覆盖后必须人工看一眼 diff 再提交 —— 这是唯一能改基线的入口，不能自动更新。

## 四、非功能需求

| ID | 要求 | 度量 |
|---|---|---|
| NFR-1 | 离线评测不花钱 | 0 次模型调用，0 token |
| NFR-2 | 离线评测快 | ≤ 2 秒（纯内存计算） |
| NFR-3 | 不引入密钥依赖 | CI 不需要 `DEEPSEEK_API_KEY`，`permissions` 仍为只读 |
| NFR-4 | 判定逻辑可测 | 对比/分类逻辑抽成纯函数，有单测覆盖 |

## 五、验收标准

**AC-1（在线正常）** 给定模型表现与基线一致，当跑 `npm run eval`，那么输出 6 条全"不变"，退出码 0。

**AC-2（真回归被拦）** 给定基线里 `hot-long` 是 passed、本次 failed，当跑 `npm run eval`，那么输出标记"退步 1 条"，退出码 1。

**AC-3（已知失败不阻塞）** 给定 `improving-trend` 在 `knownFailures` 里且本次仍失败，当跑 `npm run eval`，那么报告里明确写"已知失败"，退出码仍为 0。

**AC-4（离线一致）** 给定基线未改动，当跑 `npm run eval:offline`（且不设 API key），那么 6 条重放结果与基线完全一致，退出码 0。

**AC-5（离线发现规则被改松）** 给定把某个 `check` 的判据改宽（例如去掉"未编造信息"这一项），当跑 `npm run eval:offline`，那么该条重放结果与基线不一致，退出码 1。

**AC-6（CI 不需要 secret）** workflow 里该 step 不引用任何 `secrets.*`，且 `npm run ci` 在无 key 环境下能跑到底。

## 六、边界与失败处理

| 场景 | 期望行为 |
|---|---|
| 无 `server/.env` 且无 key，跑在线评测 | 明确提示"未配置 DEEPSEEK_API_KEY"，退出码 2，不伪装成通过 |
| 基线文件缺失 | 离线评测报错退出（1），提示先跑一次在线评测生成基线 |
| 模型超时/降级到规则引擎 | 该条记为 failed，并在报告里标 `source: fallback`，与"编造"区分开 |
| 用例数量变化（新增/删除） | 基线里多出的用例视为"未覆盖"，报告提示，不阻塞 |

## 七、对上游三个开放问题的决策

| 问题 | 决策 | 理由 |
|---|---|---|
| 基线进仓库？ | **进** | 它是离线模式的唯一数据源；不进就没法在无 key 的 CI 里做任何检查。且内容是虚构评测数据，无隐私 |
| 离线模式守什么？ | **只守判定规则不回归** | 模型质量只能靠真跑；混为一谈会制造"假安全" |
| 那条编造本轮修不修？ | **不修，记为 knownFailures** | 改 prompt 会牵动其余 5 条的判定，属于独立的一次调优；本期先把"能发现"这件事做实 |

## 八、不在本期范围
