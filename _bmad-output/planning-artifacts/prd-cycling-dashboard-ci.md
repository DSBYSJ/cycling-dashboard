# PRD · 提交即验证的 CI 流水线

> 产出工作流：`/bmad-prd`（PM）
> 上游：`brief-cycling-dashboard-ci.md`
> 版本：v1.0（2026-11-04）｜状态：已确认，交 `/bmad-architecture`
> 项目：骑行评分监测看板（cycling-dashboard）

---

## 一、目标复述

把"跑不跑测试"从**人的记性**变成**机器的判定**。任何一次 `push`（任意分支）或向 `main` 的 PR，自动依次执行 lint → 测试 → 构建；任一道不过，流水线红。

## 二、用户故事

| ID | 作为 | 我希望 | 以便 |
|---|---|---|---|
| US-1 | 站长 | 推完代码两分钟内知道有没有搞坏 | 不用自己记得跑测试 |
| US-2 | 站长 | 失败时直接看到是 lint / 测试 / 构建哪一道挂了 | 不用翻整段日志 |
| US-3 | 站长 | 在本地跑**和流水线完全一样**的命令 | 不用等推送才发现问题 |
| US-4 | 仓库访问者 | README 一眼看到"最近一次是绿的" | 5 分钟内判断这仓库的健康度 |
| US-5 | 站长 | 需要手动部署时能直接下载 CI 构建的产物 | 避免"本地旧 dist 传上去"的历史问题 |

## 三、功能需求

### FR-1 触发条件（P0）

- `push` 到**任意分支**时触发。
- 向 `main` 发起 `pull_request` 时触发。
- 同一分支连续推送时，**取消**上一次仍在跑的任务（`concurrency` + `cancel-in-progress`），避免旧提交占着队列。

### FR-2 运行环境（P0）

- 运行器：`ubuntu-latest`。
- Node：`22.x`（**与本地开发环境一致** —— 本地实测 `v22.22.2`，版本不一致是"本地绿、CI 红"的头号原因）。
- 在 `package.json` 增加 `engines.node` 声明，把"支持哪个 Node"从口头约定变成可查字段。

### FR-3 依赖安装（P0）

- 用 `npm ci`，不用 `npm install`：锁文件即事实，安装结果可复现。
- 启用 `actions/setup-node` 的 `cache: npm`，按 `package-lock.json` 的哈希缓存 `~/.npm`。

### FR-4 三道闸门（P0）

串行执行，**前一刀不过立刻停**：

| 顺序 | 闸门 | 命令 | 语义 |
|---|---|---|---|
| 1 | 静态检查 | `npm run lint -- --max-warnings=0` | 秒级反馈；当前仓库 0 警告，可以严到"警告即失败" |
| 2 | 单元测试 | `npm test` | 182 个用例，实测 19.5 秒 |
| 3 | 类型 + 构建 | `npm run build`（含 `tsc -b`） | 日常 `vite dev` 不做类型检查，这是**唯一拦得住类型错误的地方** |

### FR-5 单一入口（P0）

新增 `npm run ci`，内容就是上表三条命令的串联。**workflow 里只调用 `npm run ci`**，不再重复写命令。

> 理由（这是本次最关键的设计判断）：把闸门写在 npm script 里，本地和云端执行的是同一份脚本。换 CI 平台（GitHub Actions → Gitee Go → 自建 runner）只需换壳，闸门本身零改动；也不会出现"CI 能过，本地跑不起来"的双轨。

### FR-6 产物留存（P1）

- `dist/` 作为 artifact 上传，保留 7 天，命名 `dist-<commit 短哈希>`。
- 仅在**三道门全绿**后才上传（红灯时的产物不该被当成可发布物）。

### FR-7 状态可见（P1）

README 标题下方加流水线状态徽章（`main` 分支）。

### FR-8 失败可诊断（P1）

- 每个闸门是独立的 `step` 且带中文 `name`，GitHub 的失败摘要里能直接看到挂在哪一步。
- 不做"把日志再落一份 artifact"—— Actions 已保留完整日志，重复存储是浪费。

## 四、非功能需求

| ID | 要求 | 度量 |
|---|---|---|
| NFR-1 | 速度 | 热缓存下全流程 ≤ 5 分钟；超时必须由 `timeout-minutes` 兜住（设 15） |
| NFR-2 | 权限最小化 | workflow 声明 `permissions: contents: read`，不需要写权限 |
| NFR-3 | 可迁移 | 闸门全部在 `package.json` 的 script 里，YAML 只做"装环境 + 调脚本" |
| NFR-4 | 不泄露 | workflow 中不出现服务器地址、域名、备案号、任何密钥（沿用 `.gitignore` 里对 `server/scripts/`、`server/README.md` 的既有约定） |

## 五、验收标准

**AC-1（绿）** 给定 `main` 上的正常代码，当我 push，那么三个 step 全绿，且总时长被记录。

**AC-2（lint 拦得住）** 给定一处未使用变量，当我 push，那么第 1 步失败，第 2、3 步被跳过（不是跑完再报错）。

**AC-3（类型拦得住）** 给定一处类型错误（lint 语法层面查不出、`tsc` 才报的那种），当我 push，那么第 1、2 步通过、第 3 步失败。

**AC-4（警告即失败）** 给定一处只产生 warning 的代码，当 lint 带 `--max-warnings=0` 执行，那么返回非零退出码。

**AC-5（本地等价）** 在本地执行 `npm run ci`，退出码与云端同分支结果一致。

**AC-6（产物）** 绿跑结束后可在 Actions 页面下载 `dist-<sha>`，解压后是可直接部署的静态文件。

## 六、边界与失败处理

| 场景 | 期望行为 |
|---|---|
| 依赖安装失败（网络/npm 源） | 停在"装依赖"步，不进入闸门；重跑即可，不消耗后续时间 |
| 测试用例本身不稳定（flaky） | 先记录，不擅自加重试掩盖问题。当前 182 用例本地稳定，若 CI 出现抖动按缺陷处理 |
| 只改文档的提交 | 仍然跑（全流程约 2 分钟，不值得为省这点时间引入 `paths-ignore` 漏跑风险） |
| 分支被删 / PR 关闭 | 由 `concurrency` 自动取消，无需额外处理 |

## 七、对上游四个开放问题的决策

| 问题 | 决策 | 理由 |
|---|---|---|
| build 与 test 是否并行 | **不并行** | 三道门总耗时约 30 秒（不含装依赖），并行省不下可感知的时间；串行才能保证"第 1 步挂了第 2 步不跑"的语义 |
| lint 是否严格到警告即失败 | **是**，`--max-warnings=0` | 基线本来就是 0 警告，此刻立规矩成本最低；等积累了几十条警告再收紧就没人愿意收了 |
| 是否设分支保护 | **不设** | 单人私有仓库设保护需要额外套餐，且会把自己锁在外面；改用"徽章可见 + 本地同命令"的自律方案 |
| 失败日志是否落 artifact | **不落** | Actions 默认保留日志，重复存储无收益 |

## 八、明确不在本期范围

自动部署、覆盖率门禁、多 Node 矩阵、Docker 化、夜间定时构建 —— 均见 `brief` 第五节，理由不重复。
