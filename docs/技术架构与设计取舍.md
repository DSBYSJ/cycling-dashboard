# 技术架构与设计取舍

> 这份文档是给「讲这个项目」用的 —— 面试、答辩、或者写进简历附件。
> **全部内容都能在代码里找到对应**，没有夸大。每条决策都按「问题 → 选择 → 代价」写，
> 因为面试官真正想听的往往不是你用了什么，而是**你为什么这么选、为此放弃了什么**。

---

## 一、一句话定位

一个自己写、自己用的骑行数据看板：把骑行记录、当天的天气与路线条件、装备状态收在一处，
用一套统一的评分模型让不同时间的骑行可以横向比较；并把同一套模型用到未来 7 天的预报上，
回答"这几天什么时候出门最合适"。

**形态**：React SPA + Node API + SQLite，同源部署在阿里云一台 2 核 2G 的 ECS 上，
有域名、HTTPS、ICP 与公安联网备案，是个**真正在线上跑着**的服务，不是本地 demo。

---

## 二、整体架构

```
浏览器（React 18 + TS + Vite + Tailwind）
   │  httpOnly Cookie 会话，无需前端管理令牌
   │  PWA：离线可看缓存、可安装到桌面
   ▼
Nginx（静态前端 dist/  +  /api 反向代理）
   ▼
Node 22 + Fastify 5（TypeScript 直接运行，无构建步骤）
   ├─ node:sqlite   本地文件数据库（零原生模块）
   ├─ node:crypto   scrypt 加盐哈希
   └─ JWT + httpOnly Cookie 会话
   ▼
SQLite（WAL 模式，每天定时 VACUUM INTO 一致性快照备份）
```

**外部依赖只有两个免 Key 的公开 API**：Open-Meteo 的天气与空气质量
（历史记录与未来预报都用它，所以有网就能用，也不需要申请密钥）。

## 三、关键技术决策

### 1. 后端坚持"零原生模块"

- **问题**：便宜的云服务器上编译原生模块（`better-sqlite3`、`bcrypt`）经常失败 ——
  node-gyp 要 Python、要 C++ 工具链，版本一错就装不上，而这类问题在部署当天才暴露。
- **选择**：只用 Node 22 内置的 `node:sqlite` 和 `node:crypto` 的 `scrypt`。
- **代价**：必须 Node ≥ 22.6；`node:sqlite` 的 API 比 better-sqlite3 朴素，一些便利方法要自己写。
- **收益**：`npm install` 永不编译，换机器、重装、扩容都不用担心环境。整个证书链条上少了一环。

### 2. 登录态放 httpOnly Cookie，不放 localStorage

- **问题**：前端存 token 是 XSS 的标准攻击面 —— 一个恶意脚本就能把令牌捞走。
- **选择**：JWT 放 `httpOnly + Secure + SameSite=Lax` 的 Cookie；前端**完全不接触令牌**。
- **代价**：前端无法"不请求就判断登录态"，每次都要问后端 `/api/auth/me`；
  且必须同源部署（否则要处理 CORS + SameSite，反而更容易配错）。
- **收益**：XSS 拿不到会话；前端也不用在每次请求手动加 `Authorization` 头。

### 3. 认证钩子每次请求都回查账号状态

- **问题**：JWT 是无状态的，签发后在有效期内**无法撤销**。如果只验签名，
  管理员停用某个账号后，对方手里的 Cookie 仍能继续用满整个有效期 —— "停用"是摆设。
  这个 bug 是真实存在过的（见第五节）。
- **选择**：认证钩子里回查 `users.status`，并比对一个 `token_version` 字段
  （改密 / 重置密码 / 停用时自增），对不上就让令牌作废。
- **代价**：每个请求多一次数据库查询。
- **收益**：停用与改密**立即生效**，而不是等 30 天自然过期。
  本地 SQLite 查询是微秒级，这点开销换得来。
  另外老令牌没有 `token_version` 字段时按 0 处理，与库里的默认值一致，**升级不会把所有人踢下线**。

### 4. 用户隔离写在数据层的复合主键里

- **问题**：多租户最常见的漏洞是"某个查询忘了加 `WHERE user_id = ?`"。靠人记住是不会长久的。
- **选择**：所有业务表都用 `(user_id, id)` 作为**复合主键**，每条 SQL 都带 `user_id`。
- **代价**：主键变复杂，跨用户查询（管理员后台）要显式写出来。
- **收益**：即使某处真的漏了过滤条件，也**取不到别人的行** —— 隔离由数据结构保证，
  而不是由代码规范保证。集成测试里专门有一组用例守这条。

### 5. 索引是照查询模式设计的

- **场景**：首页与趋势图都是"取当前用户的记录，按日期倒序，再按创建时间兜底"。
- **选择**：建 `(user_id, date DESC, created_at DESC)` 的联合索引，让排序和过滤都被索引覆盖。
- **代价**：写入时多维护一个索引（本场景写入远少于读取，划算）。
- **收益**：省掉排序步骤；也说明索引不是"看到 WHERE 就加一个"，而是从查询出发倒推的。

### 6. 列表接口不返回轨迹点

- **问题**：一条 GPX 轨迹可能有几千个坐标点。列表一次返回几十条，首屏体积会直接失控。
- **选择**：列表接口只给一个 `hasTrack` 布尔标记，点开某条详情时**再单独取** `track`。
- **代价**：前端要处理"按需加载 + 与本地缓存合并"—— 这里踩过一个真实的坑（见第五节）。
- **收益**：首屏不为自己不看的数据买单。

### 7. 离线时明确拒绝写入，而不是排队重试

- **问题**：本地优先 + 后台同步看似体验好，但会立刻引出冲突解决、幽灵数据、
  以及"用户以为存了其实没存"这类问题。
- **选择**：断网时**拒绝写入并明确说明原因**；本地只保留**只读**缓存供查看。
- **代价**：离线体验"不聪明"，不能在地铁里随手记一笔。
- **收益**：用户永远清楚数据到底存没存下来。这是刻意的产品取舍 —— 宁可少一个特性，
  也不要一个会让用户怀疑数据可信度的特性。

### 8. 运行时设置与部署配置分离

- **问题**：如果"注册开关"这种运营开关放在 `.env` 里，每次调整都要改文件 + 重启服务。
  但如果把 `JWT_SECRET`、数据库路径也搬进数据库，就是**主动扩大攻击面** —— 改错一次服务都起不来。
- **选择**：分两类。
  部署期配置（`JWT_SECRET` / 数据库路径 / 端口 / Cookie 安全标志）**只留 `.env`**，
  后台不提供任何读写入口；运营期配置（注册开关、留言开关、邀请码开关）
  进 `settings` 表，后台一键切换、**无需重启**。
- **收益**：既不用为了改个开关重启服务，也不会让密钥出现在能被后台改到的地方。
  键名用白名单收窄，避免把这张表当成任意键值草稿纸。

### 9. 管理员白名单放在 `.env`，不放在数据库

- **选择**：管理员由配置里的账号白名单决定，**数据库里不存角色字段**。
- **收益**：即使数据库被注入或误改，也**提不了权**。换个管理员的成本是改配置 + 重启，可以接受。
- **配套**：权限判定一律在后端做；前端"把入口藏起来"只是体验优化，不是权限控制。

### 10. 前端图表全部手写 SVG，不引图表库

- **问题**：主流图表库动辄几百 KB，而这里只需要四种固定图形（趋势、速度曲线、海拔剖面、雷达）。
- **选择**：手写 SVG + 自己写线性插值和刻度计算（`utils/chartHelpers.ts`）。
- **代价**：没有交互式 tooltip、缩放、图例这些现成能力；每加一种图都要自己写。
- **收益**：体积可控、样式完全跟随应用主题。
- **附带一个坑**：SVG 的**展示属性不支持 CSS 变量**（`fill="var(--x)"` 在属性位置不生效），
  所以图表配色统一改成用 CSS class 驱动 —— 这样明暗主题切换时图表才会跟着变。

## 四、评分模型

综合分 = 天气适宜度 × 0.6 + 路线质量 × 0.4

- 天气维度：气温、空气质量、风速、湿度、降雨指数（降水量 × 0.6 + 降雨概率 × 0.4）
- 路线维度：累计爬升、平均坡度、路面类型、交通流量

设计上做了几件事：

1. **每个维度一个独立函数**（`temperatureDeduction`、`rainDeduction`…），
   因此每一条规则都能单独写单元测试，权重想调也只改一个常量。
2. **用"扣分制"而不是"加权和"**：从 100 分往下扣，因为"为什么少了 20 分"比
   "为什么是 82 分"更容易解释 —— 界面上的文字建议就是直接从扣分项生成的。
3. **同一套模型用在两个方向**：历史记录（事后评分）与未来 7 天预报（事前建议）
   共用 `computeWeatherScore`，所以两个面板的分数可以横向比较。
   这是这个项目里我自己最满意的一处复用 —— 换个数据源就能产出新维度的价值。

## 五、调试记录（真实踩过的坑）

这一节的每一条都是**先出现症状、再定位、最后修掉**的，适合讲"我怎么排查问题"。

### 1. 列表里点一下保存，服务器上的轨迹就被清空了

- **症状**：从列表打开一条记录、不改轨迹直接保存，之后再打开发现轨迹没了。
- **原因**：列表接口为了控体积**不返回轨迹**（决策 6），所以列表项的 `track` 是空数组；
  而保存接口是"全量替换"语义 —— 于是空的轨迹把服务器上的覆盖掉了。
- **修复**：保存前先 `GET` 一次详情，用真实轨迹拼出请求体（`toWritableRide()`）。
- **收获**：这是"接口语义"和"数据形状"组合出来的 bug，单看任何一边都不觉得有问题。

### 2. 第一次打开有轨迹，刷新一下就没了

- **症状**：进入某条记录能正常看到轨迹，刷新页面后轨迹消失。
- **原因**：负责按需加载详情的逻辑只依赖"当前选中的 id"，而刷新后 id 没变 →
  它认为"已经加载过了"，于是不去请求；但缓存里那条记录并没有轨迹。
- **修复**：依赖改成"**当前这条是否还缺轨迹**"这个布尔值，而不是只依赖 id。
- **收获**：用"做了什么动作"当缓存失效条件，比用"对象标识"当条件可靠。

### 3. 停用账号形同虚设

- **症状**：在后台停用了一个账号，对方刷新页面**仍然能用**。
- **原因**：认证钩子当时只验证 JWT 签名，从不回查数据库（决策 3 的反面教材）。
- **修复**：钩子里回查 `status` 之外，还引入 `token_version` 让改密、重置密码也能立即生效。
- **收获**：无状态令牌的代价必须在别处补回来，否则"撤销"这个能力是缺失的。

### 4. 备份功能一直显示"0 份"

- **症状**：后台的备份管理是空的，手动触发备份也失败，但目录里确实有备份文件。
- **原因**：备份目录权限是 `700` 且属主是 `root`，而服务进程以 `www` 身份运行 ——
  **连目录都进不去**。
- **修复**：改成 `750` 且属组设为服务用户所在的组。
- **收获**：这类问题在本地永远复现不了（本地就是 root），只有真实的权限模型下才会暴露。

### 5. 换账号登录后看到了上一个人的数据

- **症状**：用另一个账号登录，界面上还残留着上一个账号的离线缓存。
- **原因**：本地缓存用了固定的数据库名，与账号无关。
- **修复**：缓存按账号分库命名（`...-cache-u<id>`）。
- **收获**：缓存的"作用域"必须和数据的"可见范围"对齐。

## 六、测试策略

| 层 | 数量 | 说明 |
|---|---|---|
| 前端单元测试 | **146 个用例 / 10 个文件** | 评分算法、GPX 解析、外胎寿命、导出导入、坐标归一、API 客户端、出行窗口计算 |
| 后端集成测试 | **60 个用例** | 用真实 SQLite（内存库）+ 真实 HTTP 请求，覆盖注册登录、数据读写、**用户隔离**、权限边界 |

几个刻意的选择：

- **后端不做 mock，用真实数据库发真实请求**。因为最要命的风险是"SQL 写错"和"权限漏判"，
  这两类问题 mock 掉数据库就测不出来了。
- **权限边界是重点覆盖对象**：未登录 401、普通用户访问管理接口 403、
  停用后旧 Cookie 立即失效、重置密码后旧会话失效、不能停用自己（防自锁）。
- **算法单独测**：评分规则拆成独立函数，所以每条规则都能钉住一个具体数值，
  改权重时能立刻知道哪些用例受影响。

## 七、部署与运维

- **同源部署**：Nginx 提供静态文件 + 反代 `/api`，因此没有跨域问题，
  Cookie 的作用域也和开发环境一致（避免"开发能登录、上线登录失效"）。
- **数据库备份**：每天定时用 `VACUUM INTO` 做一致性快照 —— 它不需要停服务，
  也不会因为 WAL 模式漏掉数据。
- **进程托管**：服务以独立用户运行；同时配了开机自启与崩溃重启。
- **合规**：完成了 ICP 备案与公安联网备案，域名强制 HTTPS（证书自动续期）。
  这部分虽然不"技术"，但它意味着这个项目**真的对外提供过服务**，
  而不是一个跑在 localhost 的作业。

## 八、怎么讲这个项目

### 30 秒版

> 我独立做并上线了一个骑行数据看板。前端 React + TypeScript，后端 Node + Fastify + SQLite，
> 部署在自己的云服务器上，有域名、HTTPS 和备案，前后端一共 200 多个测试用例。
> 它不只是记录数据 —— 我用一套评分模型把天气、路线、空气质量折算成 0–100 分，
> 再把同一套模型用到未来 7 天的预报上，回答"这几天什么时候出门最合适"。

### 3 分钟版（按这个顺序讲）

1. **要解决的问题**：现有骑行 App 大多只记录数字，不回答"这次骑得值不值"。
   同样的距离，在什么天气、什么路面下骑的，体验完全不同。
2. **我的做法**：把环境与路线条件也纳入评分，让不同时间的骑行可以横向比较；
   再往前一步，因为天气可以预报，同一套模型就能用来做"出门前的建议"。
3. **一个技术决策**：讲"零原生模块"（决策 1）或"用户隔离写在复合主键里"（决策 4）——
   挑一个你能讲透的，说清楚**为什么这么选、放弃了什么**。
4. **一个排错故事**：讲第五节里任意一条。重点是**怎么从症状定位到原因**，
   而不是"我写了个 bug 然后修好了"。
5. **主动说不足**：见第十节。主动承认局限比被问出来好得多。

## 九、可能被追问的问题（准备好答案）

| 可能会问 | 回答要点 |
|---|---|
| 为什么不用 MySQL / PostgreSQL？ | 单用户为主的个人应用，数据量在单机 SQLite 的舒适区内；省掉一个独立服务的运维成本。**并且说清什么时候该换**：并发写入变多、需要多实例共享数据时，SQLite 的单写锁就是瓶颈。 |
| 用户量上来了怎么办？ | 先定位瓶颈：SQLite 写入串行是第一个天花板。路径是换 PostgreSQL → 引入 Redis 缓存热点查询 → 前端静态资源上 CDN。但**现在的量级还不需要**，提前上这些只是增加复杂度。 |
| 为什么不用 Docker？ | 当前单机部署，用面板 + 脚本已经够；Docker 的价值在多环境一致性与水平扩展，等要部署第二台时会带来收益。**这是待办，不是"没想到"**。 |
| 为什么没有 CI/CD？ | 现在是手动构建上传。这是明确的短板 —— 下一步就做 GitHub Actions：push 后自动跑测试 + lint + 构建，通过才发布。 |
| 测试是不是写太多了？ | 后端那 60 个用例里，权限边界和用户隔离占了不少。这类错误一旦上线就是数据泄露，用测试钉住比人工回归划算。算法测试则是为了改权重时能立刻发现影响面。 |
| 前端为什么不用状态管理库？ | 状态基本是"服务端数据的缓存"，用自定义 hook 封装已经足够。引入 Redux 这类方案是**为了解决问题**，不是为了让技术栈好看。复杂度真的上来时再引。 |
| 这个和你的专业（大数据）有什么关系？ | 项目里有完整的一条数据链路：**采集**（天气 / 空气质量 API、GPX 轨迹）→ **清洗**（缺失值、单位归一、时区对齐）→ **建模**（评分模型与权重设计）→ **存储**（表结构、索引、迁移）→ **展示**（可视化）→ **导出**（JSON/CSV 备份）。这正好是把课上学的数据处理流程真正走了一遍。 |
| 你一个人做的吗？ | 是。所以要如实说清哪些是查文档、看报错、反复试出来的 —— 这恰恰说明能自己解决问题。 |
| 最大的技术难点？ | 不是某个功能，而是**把"事后评分"和"事前建议"统一到一套模型上**：要保证两个方向用完全相同的口径，否则两边分数没法比。最后是把评分逻辑抽成纯函数才做到的。 |
| 如果重做，你会改什么？ | ① 一开始就把 CI 建起来；② 接口语义显式写进类型或文档（第 5 节那个"全量替换"的坑就是没写清）；③ 早一点引入端到端测试。 |

## 十、已知不足（主动说）

- **没有团队协作痕迹**：单人单分支开发，没有 PR、没有 code review。
  如果岗位看重协作，可以主动说明自己熟悉 Git 分支流程，只是这个项目没有协作者。
- **没有 CI/CD**：目前是手动构建 + 上传。这是最该补的一环，成本也最低。
- **数据量小**：真实数据只有个位数记录，**没有做过压力测试**，
  所以"性能"目前只是设计层面的，没有实测数字支撑。想补的话就是造数据压测再给结论。
- **单机部署，没有高可用**：一台 2C2G 的机器，挂了就没了。
  备份是有的（每日快照），但没有多实例与故障转移。
- **没有监控告警**：只有日志，没有指标采集和告警，出问题靠人发现。
- **前端没有端到端测试**：手写了不少无头浏览器验证脚本，但没有沉淀成 CI 里跑的 E2E 用例。
- **没做无障碍与国际化**：语义化标签和 ARIA 有一部分，但没有系统做过键盘导航与读屏验证。
