# 站长控制面板 · 功能规划

> 规划日期：2026-09-29　状态：**待确认范围后实施**
> 定位：**站长自用的运营后台**。不是用户功能，不进用户的主导航。

---

## 一、边界（先说不做什么）

| 不做 | 原因 |
|---|---|
| UGC 内容审核、删评论 | 站点合规上**不做用户间内容**（见 `docs/用户聊天功能合规评估.md`），后台自然也不需要这类工具 |
| 复杂 RBAC / 多角色权限 | 单人站长，最多加一两个协同者。一套「管理员 / 非管理员」的布尔判断足够 |
| 电商、订单、支付类模块 | 站点是非经营性个人备案，**不能有任何商业元素** |
| 「以某用户身份登录」（模拟登录） | 高危：可越权读取任意用户数据。排障需要时宁可写一次性脚本 + SSH，不要做成常驻功能 |
| 实时监控大屏、告警推送 | 运维量远未到那个规模，收益低 |

## 二、现状盘点（规划要落在已有代码上）

### 已经具备

| 能力 | 位置 |
|---|---|
| 认证钩子（把会话挂到 `request.user`） | `server/src/lib/http.ts` 的 `makeAuthHook` |
| 路由工厂插件 + 前缀注册 | `server/src/app.ts`，如 `app.register(authRoutes(db, config), { prefix: '/api/auth' })` |
| 迁移机制（只追加、按 `schema_migrations` 记版本） | `server/src/db/schema.ts` 的 `MIGRATIONS` |
| 全局限流兜底（300 次/分钟） | `app.ts` 里的 `@fastify/rate-limit` |
| 外键级联删除（删用户会连带删他的记录） | 三张表的 `REFERENCES users(id) ON DELETE CASCADE` |
| 备份脚本（`VACUUM INTO` 一致性快照） | `server/scripts/backup.mjs` |
| 前端 hash 路由 | `src/hooks/useTabRoute.ts`（目前只有 record / dashboard / bikes 三个分页） |

### 缺什么（决定了要做的改造）

| 缺口 | 影响 |
|---|---|
| **users 表没有角色字段**，`admin` 账号只是普通用户 | 必须先有管理员身份认定机制 |
| **users 表没有状态字段**（无禁用/封禁能力） | 要「禁用账号」需加字段迁移 |
| **没有「最后登录时间」** | 用户列表看不出活跃度（可选补） |
| **配置是启动时快照**（`process.loadEnvFile()` 在启动时读一次） | 「注册开关」这类要改 `.env` + 重启，**无法运行时切换** → 要引入 settings 表 |
| 没有审计表 | 管理操作无法追溯 |

## 三、管理员身份怎么认定（三选一）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 环境变量白名单**（推荐） | `.env` 里 `ADMIN_USER_IDS=6`（逗号分隔）。`makeAdminHook` 在认证后再判断 userId 是否在名单里 | 不涉及数据迁移；**改配置即生效**；数据库被改也提不了权（更安全）；代码量最小 | 换个管理员要改 `.env` + 重启；管理员多了不好管 |
| **B. users 表加 `role` 字段** | 迁移加 `role TEXT NOT NULL DEFAULT 'user'`，管理员为 `'admin'` | 可在后台自助增删管理员；以后要扩展角色方便 | 要动迁移 + 所有用户查询；存在「数据库被改成 admin」的提权路径，要靠审计兜 |
| **C. 两者结合** | 表里存 role，但首个管理员由环境变量指定（防自锁） | 兼顾自助与安全 | 稍复杂 |

**建议 A。** 理由：单人站长场景下，管理员的变更频率极低；而 A 把「谁有管理权」放在服务器文件系统里（`.env` 权限 `600 www:www`），比放在数据库里更难被利用。

无论选哪个，都要定一条硬规则：**不能通过后台把自己从管理员里移除 / 禁用自己**（防自锁），真锁死了要能靠改 `.env` + 重启恢复（A 方案天然满足）。

## 四、功能模块（按优先级分三批）

### 第一批 · MVP（站长日常真正会用的）

#### A. 概览

- 数据规模：用户数 / 记录数 / 单车数 / 打卡数
- 存储占用：数据库主文件 + WAL 大小
- 服务状态：Node 版本、进程启动时间、运行时长、常驻内存
- 近 7 天趋势：新增用户、新增记录（简单柱状）
- 最近注册的用户（5 条）

接口：`GET /api/admin/overview`

#### B. 用户管理（核心）

- **列表**：分页 + 按账号搜索 + 按注册时间/记录数排序
  每行显示：ID、账号、显示名、注册时间、记录数、单车数、打卡数
- **详情**：基础信息 + 数据统计 + 最近 10 条记录（不带轨迹）
- **禁用 / 启用账号**（需加 `status` 字段）
  禁用后：登录被拒（提示「账号已被停用」），已持有的会话立即失效
- **重置密码**：生成随机临时密码并**仅一次性显示**在页面上（不写日志、不再可查）
- **删除账号**：连带删除其全部数据（外键已 CASCADE）。**必须二次确认，且要求手动输入该账号名**

接口：`GET /api/admin/users`、`GET /api/admin/users/:id`、`PATCH /api/admin/users/:id`（改 status）、`POST /api/admin/users/:id/reset-password`、`DELETE /api/admin/users/:id`

#### C. 注册开关（现在最痛的点）

当前要改注册状态得：SSH → 改 `.env` → 重启后端。做成后台一键切换。

**技术前提**：配置现在是启动时读的快照，要实现运行时切换需要引入 **`settings` 表（key-value）**，后端判断时优先读表、miss 再回落 `.env`，并加一层进程内缓存（改动时失效）。

这一层建好后，后续所有「运行时可调」的配置都能复用（如限流阈值、是否开放注册、维护公告）。

接口：`GET /api/admin/settings`、`PATCH /api/admin/settings`

### 第二批 · 运营与可追溯

#### D. 数据浏览与统计

- 全局记录浏览：跨用户、按日期区间 / 用户 / 城市筛选、分页（**列表不带轨迹**，与用户端一致的约定）
- 单条记录详情（含轨迹）
- 删除异常记录（二次确认）
- 统计：按城市分布、按月份分布、评分离散度

接口：`GET /api/admin/rides`、`GET /api/admin/rides/:userId/:id`、`DELETE /api/admin/rides/:userId/:id`、`GET /api/admin/stats`

#### E. 备份管理

- **手动触发备份**（把 `backup.mjs` 的核心逻辑抽成可复用函数，脚本与接口共用）
- 备份列表：文件名、大小、时间、保留份数
- 删除指定备份
- 数据库自检：`PRAGMA integrity_check`、表行数、WAL 状态

⚠️ **不建议做「下载备份」接口** —— 备份文件等于整个数据库（含所有用户的密码哈希）。需要下载时走宝塔文件管理器或 SSH，多一道人工确认更安全。若一定要做，必须二次确认 + 记审计。

接口：`GET /api/admin/backups`、`POST /api/admin/backups`、`DELETE /api/admin/backups/:name`、`GET /api/admin/db-status`

#### F. 审计日志

- 新表 `admin_audit_log`：时间、管理员 userId、操作类型、目标、结果、IP
- 记录所有**写操作**（重置密码、删账号、改设置…）
- 界面：列表 + 按操作类型/时间筛选

理由：单人站也需要，因为一旦发生纠纷（比如用户说「我的数据被你删了」），日志是唯一的举证材料。成本低、价值高。

### 第三批 · 可选

#### G. 反馈 / 留言管理

若要做「用户 → 站长单向留言」（合规上完全 OK，见合规评估文档），站长需要一处查看与标记处理的界面。

- 新表 `feedback`：user_id、内容、创建时间、状态（未读/已读/已回复）、回复内容
- 用户端入口 + 站长端列表
- ⚠️ 严格保持**单向**：用户看不到别人的留言，也看不到其他人的回复

#### H. 注册邀请码

把「开放注册」换成「凭码注册」，适合只给朋友用的场景。新表 `invite_codes`（码、可用次数、有效期、已用记录）。

#### I. 系统信息与日志

- 后端日志尾部查看（最近 N 行，只读）
- 环境变量**脱敏**查看（列出键名 + 是否已配置，**绝不显示值**）
- 运行环境信息（OS、Node、SQLite 版本）

## 五、需要的数据迁移

新增一条迁移（**只追加，不改历史**）：

```sql
-- version 2
ALTER TABLE users ADD COLUMN status TEXT NOT NULL DEFAULT 'active';   -- active / disabled
ALTER TABLE users ADD COLUMN last_login_at TEXT;                       -- 可选

CREATE TABLE settings (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE admin_audit_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  actor_id    INTEGER NOT NULL,
  action      TEXT NOT NULL,
  target      TEXT,
  detail      TEXT,
  ip          TEXT,
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_audit_created ON admin_audit_log(created_at DESC);

-- 第三批才需要
CREATE TABLE feedback (...);
CREATE TABLE invite_codes (...);
```

> 注意：`settings` 表要区分「数据库里的运行时配置」与「`.env` 里的部署配置」。原则是
> **部署期决定、不该被后台改的**（`JWT_SECRET`、`DATABASE_PATH`、`PORT`、`COOKIE_SECURE`）只留在 `.env`，
> 后台**不可读不可写**；**运营期需要随手改的**（注册开关、限流阈值）才放 `settings`。

## 六、安全清单（实施时必须逐条满足）

1. **每个 `/api/admin/*` 接口都在后端校验管理员**，绝不能只在页面上藏入口（前端隐藏不是权限控制）
2. **管理接口单独限流**，阈值比普通接口更严（防口令爆破与批量探测）
3. **二次确认**：删除类操作要求手动输入目标账号名，而不是点一下「确定」
4. **防自锁**：不能禁用/删除自己；改名册时保证至少留一个管理员
5. **审计先行**：写操作先落审计再执行，避免「操作成功但没留下记录」
6. **脱敏**：任何页面与接口都不返回 `password_hash`、`JWT_SECRET`、数据库绝对路径
7. **重置密码后**只在响应里返回一次，不落日志、不可回查
8. **敏感改动要让会话失效**：禁用账号 / 重置密码后，该用户已签发的 Cookie 立即失效
9. **`.env` 里的部署密钥不进 `settings` 表**，后台不提供任何读改入口
10. 后台页面**不进主 bundle**（懒加载），普通用户不会下载到管理端代码

**留言**：先做好、默认不对外显示，站长自己测试通过后再开。

### 实施中发现、原规划没预料到的三个问题

1. **"停用"必须立即生效** —— 认证钩子原来只校验 JWT、不回查数据库，等于站长停用某人后，
   对方手里的 Cookie 还能继续用满 30 天，"停用"形同虚设。
   改为每次请求回查账号状态；同时加 `token_version`（改密 / 重置密码 / 停用时自增），
   让这些操作也能立刻把旧令牌踢下线。SQLite 本地查询是微秒级，这点开销换得来。

2. **备份目录读不到** —— 线上 `/www/backup` 是 `700 root:root`，后端进程以 `www` 运行，
   连目录都进不去，所以「备份管理」显示 0 份、手动备份也失败。
   改为 `750 root:www` 后正常（root 不受影响，宝塔自身的备份照常）。

3. **账号菜单里的密码下限没跟着放宽** —— `AccountMenu` 还写着"至少 8 位"，而后端已放宽到 6 位。
   规则不一致会让用户被前端拦住，已一并改成 6。

### 验证

- 后端 **58 个用例**（新增 15 个）：未登录 401 / 普通用户 403 / 管理员 200、
  停用后旧 Cookie 立即 403、重置密码后旧会话 401、删除需手打账号名、
  不能停用自己与白名单管理员、写操作落审计、审计不含密码、注册开关运行时切换、留言默认关闭
- 前端 **126 个用例**、lint 0 问题、构建通过
- 线上：用管理员账号实测 `/api/admin/*` 全部可用，触发备份成功，审计记录正常
- 界面：CDP 驱动真实浏览器走完「登录 → 切到站长 → 逐个面板」，四个面板渲染正常

### 有意没做

- **下载备份接口** —— 备份文件等于整个数据库（含所有密码哈希），走宝塔/SSH 取更稳
- **「以某用户身份登录」** —— 可越权读任意用户数据，排障宁可写一次性脚本

### 一个需要留意的运维点

`/www/backup` 的权限若被面板或安全加固改回 `700`，「备份管理」会重新变成 0 份。
届时执行：`chown root:www /www/backup && chmod 750 /www/backup`。
