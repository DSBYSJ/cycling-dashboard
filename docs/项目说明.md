# 骑行评分监测看板 · 项目说明

> 一份从想法到上线的个人全栈项目：**记录骑行数据 → 自动采集环境 → 计算评分 → 可视化 → AI 复盘**。
> 本文是项目总览，写给想了解它的人；技术细节另有专文，见文末「相关文档」。

| 项目 | 说明 |
|---|---|
| 定位 | 个人骑行记录与评分看板（Web 应用，支持安装到桌面 / 手机） |
| 当前版本 | `v1.0.1`（页脚可点击查看每个版本的更新内容） |
| 状态 | **已上线运行**：域名 + HTTPS + ICP 备案 + 公安联网备案 |
| 代码规模 | 应用代码 **119 个文件 / 约 1.7 万行**，测试 **18 个文件 / 约 3.7 千行** |
| 测试 | **283 个用例**（前端 181 + 后端 102），另有 AI 输出质量评测集 |
| 运行时依赖 | 前端 **7 个**、后端 **4 个**（刻意保持极少） |

---

## 一、为什么做它

现有骑行 App 大多只记录数字 —— 距离、速度、时间。但它们很少回答一个真正有意思的问题：**这次骑得值不值**。

同样的 30 公里，在 30℃ 高温与 18℃ 阴天之间、在平路与 400 米爬升之间、在车流密集与沿江绿道之间，体验完全不同。脱离环境条件看数字，不同时间的骑行无法横向比较。

所以这个项目把**天气、空气质量、路线海拔与坡度**也纳入评价体系，让一次骑行得到一个可比较的综合分，并解释「为什么是这个分、下次能怎么改进」。

做到后来，它又往前走了一步：不仅能事后评价，**还能在出门前告诉你哪天哪个时段最适合出去**（未来 7 天出行建议），以及**用大模型针对这一次骑行给出训练建议**（AI 教练）。

## 二、功能全景

### 记录与采集

| 功能 | 说明 |
|---|---|
| 三种录入方式 | 手动填写表单 / 导入 GPX 轨迹文件 / 在地图上绘制路线 |
| 今日打卡 | 只想记一笔"今天骑了吗"时，一步完成，详细数据可后补 |
| 自动采集环境 | 按骑行地点与时段拉取天气（Open-Meteo）与空气质量；拿不到时允许手填 |
| 轨迹抽稀 | 三四万点的 GPX 会在保存前自动精简（见「关键设计」），不会因超限而存不进去 |
| GPX 指标校准 | 优先采用设备写在 `<extensions>` 里的权威统计，并对速度序列做中位数滤波去噪 |

### 评分与分析

| 功能 | 说明 |
|---|---|
| 综合评分 | 天气适宜度 ×0.6 + 路线质量 ×0.4，另给出降雨指数 |
| 分项与雷达 | 三轴雷达图：天气适宜度 / 路线质量 / 骑行表现 |
| 文字评价与建议 | 自动生成评价与改进建议，而不只是一个数字 |
| 图表 | 评分趋势、速度曲线、海拔剖面、近 6 周里程 —— **全部手写 SVG，未用图表库** |
| 地图 | 高德 JS API 展示轨迹，随昼夜主题切换底图 |
| **未来 7 天出行建议** | 拉未来 7 天逐小时预报，用同一套评分算法挑出每天最值得出门的时段 |

### 装备管理

- 单车与外胎寿命台账，按里程与使用时长双条件跟踪
- 保养提醒（超期 / 接近寿命分级提示）
- 导出备份时一并带走

### 数据与账号

| 功能 | 说明 |
|---|---|
| 云端账号 | 注册 / 登录，数据存在自己的服务器上，换设备登录即见 |
| 离线可用 | 浏览器里保留一份**只读**缓存（按账号分库），断网仍能翻看历史 |
| 导入导出 | JSON / CSV 导出；备份文件导入前逐条校验，脏数据不会进库 |
| 旧数据迁移 | 老版本存在 IndexedDB 的数据，登录后自动迁到云端（**始终不删除本地数据**） |

### AI 教练（DeepSeek）

针对某一次骑行，生成结构化复盘：摘要、做得好的、可以改进（含具体做法）、下次目标、风险提示。

- **可切换复盘对象**：卡片里有下拉直接选要复盘哪次骑行
- **不自动生成**（用户点了才调用，每次调用都是成本）、**换记录清空结果**
- ⚠️ **只对站长本人开放** —— 个人主体备案不能面向公众提供生成式 AI 服务（见「合规边界」）

### 站长控制台（仅管理员）

站点概览与运行开关、账号管理（停用 / 改密 / 临时密码）、数据浏览与统计、备份管理、审计日志、用户留言、邀请码、后台日志。

> 后台改动**运行时即时生效**，不必登服务器改配置再重启。

## 三、技术栈

**前端**：React 18 + Vite 5 + TypeScript + Tailwind CSS 3（配色走语义化 token，昼夜两套值由 CSS 变量提供）
**图表**：手写 SVG（折线 / 面积 / 雷达 / 柱状 / 环形），无图表库
**地图**：高德地图 JS API 2.0
**后端**：Node 22 + Fastify + `node:sqlite` + httpOnly Cookie（TypeScript 直跑，无构建步骤）
**存储**：SQLite（业务数据）/ IndexedDB（仅离线只读缓存）
**测试**：Vitest + jsdom（前端）、Node 内置 test runner（后端）
**PWA**：`vite-plugin-pwa`（Workbox），可安装到桌面 / 手机主屏

**依赖刻意保持极少**（前端运行时 7 个、后端运行时 4 个）：图表、日期、HTTP 客户端、加密、ORM 全部自己实现或用标准库 —— 少一个依赖，就少一份供应链风险与体积负担。

## 四、关键设计（挑几条最能说明思路的）

1. **零原生模块**
   不用 `better-sqlite3` / `bcrypt`，改用 Node 内置的 `node:sqlite` 与 `node:crypto` scrypt。
   **代价**是不能用成熟的库；**收益**是部署到便宜的云服务器上时不会出现编译原生模块失败 —— 这类问题往往只在部署当天暴露。

2. **用户隔离写进主键**
   所有表用 `(user_id, id)` 复合主键，隔离由数据结构保证，而不是靠"记得写 WHERE"。

3. **认证钩子每次回查账号状态**
   不只验 JWT，而是每次请求回查账号是否停用；配合 `token_version` 让停用 / 改密**即时踢下线**。
   否则"停用账号"会形同虚设 —— 已签发的令牌在过期前照样能用。

4. **登录态放 httpOnly Cookie**
   前端不持有令牌，XSS 偷不走；代价是必须同源部署。

5. **轨迹抽稀在上限之内进行，而不是提高上限**
   服务端有两条独立的 2 万点上限（轨迹 + 速度序列）。前端保存前用 **Douglas-Peucker** 自动精简，
   并明确提示"已自动精简轨迹点 30000 → 1296 个"，**不静默改数据**。上限本身刻意不动 —— 它是安全边界。

6. **AI 上下文压缩 >1000 倍**
   一条带 2 万轨迹点的记录超过 1MB，直接送进模型既贵又容易超窗。先把数据压成结构化 facts（不到 1KB），
   轨迹点、逐点速度、坐标一律不进 prompt。

7. **AI 失败必须降级，且降级要说清楚**
   模型超时 / 限流 / 格式错误时，回落到规则引擎已有的建议，并标注「**不是 AI 生成的**」——
   冒充 AI 比没有 AI 更糟。

## 五、数据与算法

### 评分模型

```
综合分 = 天气适宜度 × 0.6 + 路线质量 × 0.4
```

- **天气适宜度**：气温、湿度、风力、降水、空气质量（AQI）分项打分
- **路线质量**：累计爬升、平均坡度、路面类型、车流量
- **降雨指数**：降水量 ×0.6 + 降雨概率 ×0.4（单独给出，不并入总分）

### GPX 处理

设备写在 `<extensions>` 里的统计（`totalDistance` / `totalTime` / `cumulativeClimb`）**优先于自算**。
实测一份 34,701 点的华为 GPX：自算的均速会因"拿首尾时间差当骑行时长"而低估约 31%（把休息也算进去了），
最高速则会因单段采样噪声给出 92 km/h 这种假值。改用设备统计 + 中位数滤波后，各项与官方统计一致。

### AI 复盘的工程要点

结构化输出（要求返回 JSON + 逐字段校验，**校验失败绝不返回半成品**）、失败降级、上下文压缩、
缓存（键含记录版本，改了记录自动失效）、限流、可观测性（每次调用的耗时 / 尝试次数 / token 数）。

## 六、质量保障

| 类别 | 数量 | 覆盖内容 |
|---|---|---|
| 前端单测 | 181 例 | 评分规则、GPX 解析、坐标归一、图表辅助、备份校验、轨迹抽稀、API 客户端错误映射、切块、更新日志数据 |
| 后端单测 | 102 例 | 认证与权限、数据隔离、设置开关、AI 编排与结构化校验、评测判定规则、备份 |
| **AI 输出评测集** | 6 用例 × 6 项检查 | `npm run eval`，任一不达标退出码 1，**可直接挂 CI** |

评测集是这套测试里比较特别的一块：它把"模型输出好不好"变成可自动回归的问题。
判定规则本身也有单元测试 —— 用「一条好输出 + 一条水货输出」对照，确保规则真有区分能力。
（实测踩过 `includes('3')` 被 `33.5` 误中，导致 6/6 假通过 —— **判定写错，整份报告都是假的**。）

## 七、部署与运维

- 前后端**同源部署**：Nginx 提供静态资源，并把 `/api` 反向代理到 Node 后端
- 发布方式：本地 `npm run build` → 上传产物与改动的后端文件 → 重启后端（后端跑 TypeScript 源码，无需编译）
- 数据库每天凌晨自动备份（`VACUUM INTO` 一致性快照，无需停服务）
- 版本号由 `package.json` 单一来源注入；升位用 `npm run bump:patch` / `bump:major`

> 部署相关的具体路径与操作方式不在本仓库文档里（见「合规边界」）。

## 八、合规边界

站点为**个人主体 ICP 备案**，属非经营性、不能有 UGC。因此：

| 能做 | 不做 |
|---|---|
| 个人记录与展示 | 用户间聊天、公开评论 / 留言板（需手机号或身份证实名，邮箱不在其列） |
| 静态工具页 | 公开路书社区、排行榜 |
| 用户 → 站长单向留言 | **面向公众的 AI 对话**（需大模型服务登记，个人主体不能申报） |
| **仅自己可见的 AI 功能** | 可对外传播的 AI 生成内容（导出 / 分享） |

AI 功能在代码层**只对管理员开放**（后端权限钩子 + 前端渲染各挡一次），
备案信息只从环境变量读取、不写进源码。

## 九、已知不足与后续方向

如实列出，便于评估：

- **无 CI/CD**：测试与构建目前是手动跑
- **无真实用户**：数据都是本人产生，未经过真实场景压力
- **无性能实测与监控告警**：没有压测数据，也没有服务健康告警
- 提交集中在 16 天内（39 个提交），属于短期密集开发
- 后端请求体上限 8MB，数据量极大时首次批量上传可能撞上
- 华为 Health Kit 同步：**尚未申请通过**，后端已预留

可能的下一步：CI/CD（提交即跑测试）、骑行数据 RAG 问答、多运动类型、年度报告导出长图。

## 十、本地运行

```bash
# 后端（另开一个终端，需要 Node ≥ 22.6）
cd server && cp .env.example .env && npm start

# 前端
npm install && npm run dev

# 测试
npm test                 # 前端（沙箱/并发异常时用 --no-file-parallelism）
cd server && npm test    # 后端
cd server && npm run eval  # AI 输出质量评测（需要配 API Key）
```

> 本地没有 HTTPS 时，把 `server/.env` 里的 `COOKIE_SECURE` 改成 `false`，否则登录态写不进 Cookie。
